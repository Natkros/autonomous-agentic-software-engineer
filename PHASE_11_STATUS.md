# Phase 11 Status — Pipeline Wiring &amp; Production Hardening

This phase is not part of the original 10-phase roadmap (see `README.md`'s
roadmap section) — it is a follow-up requested after Phase 10 to (1) wire
the previously-standalone Phase 5/6/7 machinery into the actual agent
pipeline instead of stopping at "propose a patch," (2) add real
production-hardening concerns Phase 1 explicitly deferred, and (3) deploy
a live instance with a real Anthropic API key. Following this project's
own documentation discipline, everything below distinguishes what was
actually run and verified from what's real-but-unverified or out of
scope.

## Done and verified

- [x] **The agent pipeline is wired end to end.** `core/orchestration/graph.py`
  gained a real `execution_node`, run after the Coder: it reviews every
  proposed patch (`CodeReviewAgent`), applies and tests the approved ones
  through the real Phase 5 self-correction loop, runs a whole-workspace
  security scan (`SecurityAgent`) as a finalization gate, and — only if
  the active `AutonomyLevel` allows `GIT_WRITE` — commits via the real
  `GitCommitTool`. Every step that exceeds the current autonomy level
  produces a structured `ApprovalRequest` (`core/policies/approval.py`)
  instead of running silently. At the conservative default
  (`LEVEL_1_SUGGESTIONS`), behavior is unchanged from Phase 10: patches
  are proposed, nothing is written.
- [x] **Verified with a real git commit, not a mock.** `core/tests/test_execution_node.py`
  runs the full pipeline against a real, freshly-`git init`'d temporary
  copy of the sample fixture repository at `LEVEL_5_FULL_AUTONOMY`, and
  independently re-reads the repository's own `git log` to confirm the
  commit actually landed — the same verification discipline
  `tools/tests/test_git_write_tools.py` established for `git.push` in
  Phase 7. A second test confirms `LEVEL_1_SUGGESTIONS` reviews but
  writes nothing. `apps/api/tests/test_tasks.py` repeats both scenarios
  through the real `/api/tasks` endpoint end to end.
- [x] `POST /api/tasks` gained an `autonomy_level` field (0-5, default 1)
  and `TaskRead` now returns `review_results`, `correction_results`,
  `security_scan_result`, `approval_requests`, `git_commit`, and
  `execution_status` — the `tasks` table gained matching columns.
- [x] **Real Alembic migrations**, closing a gap flagged since
  `PHASE_1_STATUS.md` ("No Alembic migrations yet ... deferred to a later
  phase"). `apps/api/migrations/` holds a real, autogenerated initial
  migration reflecting the exact current schema (verified by applying it
  to a fresh SQLite database and confirming every table exists);
  `app/main.py`'s startup now runs `alembic upgrade head` against
  whichever `DATABASE_URL` the app itself uses (`migrations/env.py` reads
  it from `app.config.get_settings()`, never a hardcoded value) instead of
  `Base.metadata.create_all`. The test suite is unaffected — its fixtures
  build the schema directly from the SQLAlchemy models, independent of
  Alembic, exactly as before.
- [x] **Rate limiting on `/api/auth/register` and `/api/auth/login`**
  (`app/rate_limit.py`, via `slowapi`), the only two endpoints reachable
  without a bearer token and therefore the natural target for credential
  stuffing. Returns the same `{"error": {...}}` envelope every other
  error response uses. Disabled under `ENVIRONMENT=test` so the test
  suite's dozens of rapid register/login calls are never throttled;
  `apps/api/tests/test_production_hardening.py` verifies both that this
  exemption is actually wired *and* that the underlying mechanism itself
  genuinely blocks excess requests, using a separate, enabled `Limiter`
  instance against a throwaway app.
- [x] **Fail-fast production config validation** (`app/config.py`): a
  deployment with `ENVIRONMENT=production` still running the well-known
  default `JWT_SECRET` now refuses to start, rather than silently serving
  traffic with a secret every clone of this public repository already
  knows. Verified directly (`test_production_with_default_secret_raises_at_startup`)
  and confirmed *not* to fire for local development, where the default
  secret is fine.
- [x] `infrastructure/docker/api.Dockerfile` now copies `migrations/` and
  `alembic.ini` — a real gap that would have otherwise broken the new
  migration-on-startup behavior inside the container, caught before
  pushing by re-reading the Dockerfile against what `main.py`'s
  `run_migrations()` actually needs at runtime.
- [x] **Test count**: `core` grew from 64 to 67 (new `test_execution_node.py`),
  `apps/api` grew from 25 to 32 (2 new pipeline-wiring tests in
  `test_tasks.py`, 5 new hardening tests). **278 tests total**, all
  re-verified in clean Python 3.12 virtual environments.
- [x] **A real deployment, with a real Anthropic API key**, on Render:
  - `forgeai-db` — a managed Postgres 16 instance.
  - `forgeai-api` — the real `infrastructure/docker/api.Dockerfile`
    image, built and run by Render directly from this GitHub repository
    (the same Docker build CI has verified since Phase 10, now also
    verified by a second, independent build system), with a live
    `ANTHROPIC_API_KEY` set — the first time in this project's history
    `AnthropicLLMProvider` has ever actually been exercised, rather than
    documented as real-but-unverified.
  - `forgeai-web` — the real `infrastructure/docker/web.Dockerfile` image,

  See `RUNNING.md` for the live URLs, exactly what was verified against

## Explicitly NOT done in this phase

- **`execution_node` never pushes to a remote.** It commits locally
  (inside whichever workspace the pipeline is already operating on —
  a throwaway clone for `/api/tasks`), but `git.push` is deliberately not
  called: pushing to a repository's real remote on the agent's own
  initiative, with no PR/approval step in front of it, is a materially
  bigger trust decision than committing to a local clone that gets
  deleted at the end of the request. Wiring in `git.push` +
  `GitHubPullRequestClient` (real since Phase 7, still never exercised
  against a live token) into an actual "open a PR" flow remains future
  work.
- **The security/review gates use the same original, small rule set from
  Phase 6** — no new detection capability was added here, only the
  wiring that makes those existing, tested agents actually run as part of
  a task.
- **Rate limiting is in-memory, single-process.** `slowapi`'s in-memory
  store does not share state across multiple instances — irrelevant at
  the current `numInstances: 1` Render deployment, but would need a
  shared backend (Redis) to hold correctly if scaled horizontally later.
- **No background job queue.** `/api/tasks` still runs the full pipeline
  (now including execution) synchronously on the request thread. A task
  that triggers several self-correction iterations against a large
  repository can make this endpoint slow — acceptable for this
  deployment's scale, not for production traffic at volume.
- **The live deployment has no custom domain, and Render's own TLS
  termination is used as-is** — `infrastructure/nginx/nginx.conf` (real,
  syntax-verified since Phase 10) is not part of this deployment; Render
  terminates HTTPS itself in front of each service.
- **Free-tier Postgres expires in 30 days** unless upgraded to a paid
  plan before then — a real, time-bound limitation of this specific
  deployment, not a code gap. See `RUNNING.md`.
